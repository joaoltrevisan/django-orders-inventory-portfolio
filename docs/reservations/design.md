# Reservation expiry contract

## Assessment and conflicts

Starting revision: `d4d8ee1`, API 1.1.0 with 157 executed PostgreSQL tests, scoped creation idempotency and reviewed lifecycle services. Reuse its atomic stock deduction, protected history, unique order/offer release movement, ordered locks, current authorization and controlled separate-connection tests. Historical Olist clocks/statuses/payments remain untouched.

Current code recognizes a release only for CANCELLED and treats any other nonpending/noncancelled state as a repeated payment. Both assumptions must explicitly include/reject the new EXPIRED state. The status/timestamp CHECK, history inspection, API schema and documentation need corresponding changes. Pending inventory liability must continue including overdue orders until an actual release; filtering liability by the clock would allow stock capacity violations.

## Rules defined before implementation

- Every new service-created operational order receives an immutable `reservation_expires_at = created_at + 30 minutes`, using aware UTC timestamps. Thirty minutes is a demonstration policy, not an Olist source/business fact. Clients cannot choose or extend it. Existing orders retain NULL and have no automatic deadline; no backfill changes their history. Raw privileged writes remain outside service guarantees.
- PENDING_PAYMENT may become PAID only when the authoritative PostgreSQL wall clock, read after acquiring the order lock, is strictly earlier than its nonnull deadline. At equality or later, return 409 `reservation_expired`, without creating payment, changing status or releasing stock. NULL legacy deadlines remain payable. The eligibility decision linearizes under the order lock; a payment accepted before the boundary can commit afterward. `paid_at` records the decision time and must be earlier than the deadline when present.
- Overdue PENDING_PAYMENT remains pending and its stock remains deducted until cancellation or the explicit expiry command commits. GET/replay does not mutate, renew or release anything. No background scheduler or implicit client-driven expiration is introduced. A delayed/absent command delays availability; it never permits late payment.
- Cancellation remains permitted while pending, including overdue orders. Cancellation and expiry compete under the same order lock: the winner commits CANCELLED or EXPIRED and one release; neither terminal state can become the other. Existing consistent cancellation repetition remains valid. EXPIRED is terminal: payment, shipping, delivery and cancellation reject it. A keyed replay returns the same expired order and original deadline/snapshots; a new intended purchase requires a new key.
- Expiry is an explicit bounded management command, `expire_reservations`, requiring an exact `--expected-database`, an active staff `--actor-email` and `--limit` from 1 to 1000 (default 100). Run it through the API database role. No fictitious system actor or customer attribution is created. The command rechecks current administrator authority before each attempt and after waits before release writes. Inactive customers/catalog do not prevent restoration.
- Discovery captures a PostgreSQL `clock_timestamp()` cutoff for the invocation. Each attempted due pending order has its own transaction: select one row ordered by deadline/ID with `FOR UPDATE SKIP LOCKED`, then inspect its history, acquire seller/product/offer/stock locks in the existing ascending hierarchy, reconcile stock/headroom and recheck clock/authority. Never hold multiple order locks before stock locks. Locked rows may be skipped; the report cannot claim all due orders were processed. IDs already attempted are excluded, so a corrupt oldest order cannot loop forever. Limit bounds attempts, not scanned rows or wall-clock duration.
- A successful expiry atomically restores all item quantities, appends one positive RELEASE per offer with the explicit administrator and an English expiry reason, sets EXPIRED/`expired_at`, and leaves purchase snapshots, creation key and deadline intact. Existing release uniqueness protects exact-once restoration alongside row locks. Timestamps use database wall time; `expired_at >= reservation_expires_at` and no payment/shipment/cancellation timestamp is allowed in EXPIRED.
- Any write/history/stock failure rolls back that order completely. Other previously committed attempts remain committed. Emit a sanitized JSON report with cutoff, attempted/expired/skipped IDs and failures; a report containing failures produces a nonzero command exit. Authorization loss stops further work. Do not expose raw SQL, credentials, customer addresses or login responses. No automatic retry of an ambiguous command commit is claimed; rerun safely discovers remaining pending rows, while committed expired rows cannot release again.
- Add nullable deadline/expiry fields and update local CHECKs; retain legacy NULL compatibility. No speculative performance index or source query benchmark claim is included. The bounded queue may still scan/sort many rows; measure actual workload before index adoption. No setting/dependency upgrade, real payment, refund, seller suborder or production deployment enters scope.

The shared hierarchy remains optional creation-key advisory lock → existing order → sellers → products → offers → stock, each group ordered. Expiry never takes a creation-key lock. Replays wait only for the existing order and return cached coherent snapshots. `clock_timestamp()` is deliberately used instead of transaction-stable `CURRENT_TIMESTAMP`, so waiting cannot preserve a stale eligibility clock. PostgreSQL documents [wall-clock functions](https://www.postgresql.org/docs/17/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT) and [SKIP LOCKED queue semantics](https://www.postgresql.org/docs/17/sql-select.html#SQL-FOR-UPDATE-SHARE); Django documents [transactional row locks](https://docs.djangoproject.com/en/5.2/ref/models/querysets/#select-for-update).
