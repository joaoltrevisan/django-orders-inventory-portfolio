# Optional reservation expiry worker

## Assessment and reuse

Starting revision: `0b6729c`, API 1.2.0, 184 executed PostgreSQL tests, explicit audited expiry and current SQL/schema/HTTP evidence. The batch already provides one-order transactions, SKIP LOCKED discovery, failure isolation, current administrator checks and exact-once release. Reuse it; do not introduce a second lifecycle engine, queue, global lease, migration or dependency. Historical Olist data and dated index measurements are unchanged.

Default Compose and isolated CI currently have exactly five services. An optional worker must live in a separate overlay so default startup never enables it and CI cannot silently acquire a recurring process. Cross-file YAML anchors are unavailable; use an explicit small service with the same restricted API database role, nonroot/read-only application image, private network and no ports or host mounts. Existing accounts/volumes are preserved.

## Rules before implementation

- Add `run_reservation_expiry` with exact `--expected-database`, explicit active staff `--actor-email`, batch `--limit` 1–1000, `--interval-seconds` 1–3600 (default 60) and optional `--max-cycles` 1–10000. Absence of max-cycles means unlimited; explicit zero is invalid. Validate options before work. First cycle runs immediately, then fixed delay starts after each cycle completes. No overlapping cycles in one process and no catch-up burst.
- Each cycle establishes a fresh connection, confirms database and `olist_api`, resolves/revalidates the current administrator, and reuses the batch. Do not create a system actor or infer source-customer ownership. Multiple worker processes/manual commands remain safe through existing order/stock locks; no claim of exclusive execution or complete sweep follows.
- On each fresh connection set worker-only 5-second lock and 15-second statement timeouts using bound `set_config`. These limit individual statements, not total cycle/transaction time. No setting changes apply to API/manual-command sessions. Connections close after each cycle, including failures, so the next cycle reconnects and revalidates.
- Database errors produce sanitized cycle output and another attempt only after the configured delay; SQL, DSNs, passwords, tokens and customer details are not logged. Configuration/target/role/administrator errors fail fast with nonzero exit. Partial batch failures remain explicit, with committed successes retained; they are not silently turned into success or retried in a hot loop. An optional finite invocation exits nonzero if its last cycle failed; earlier failures remain visible even after recovery. Graceful signal shutdown exits normally and is not evidence that the queue drained.
- SIGTERM/SIGINT handlers set a stop event only. Interrupt waiting immediately. An optional batch stop predicate is checked before each next order, never as an exception inside a transaction; finish the current release before stopping. Record `stopped` in the batch/worker result. Restore previous signal handlers and close connections in `finally`. Docker's 30-second grace is best effort: forced termination can interrupt work; PostgreSQL rolls back uncommitted writes, and a subsequent run never releases an already committed expired order twice. No strict shutdown-duration guarantee follows from per-statement timeouts.
- Emit sanitized JSON startup, cycle-start/cycle-finish and shutdown events with cycle number, monotonic elapsed seconds, aggregate attempted/expired/skipped/failure counts, failure-code counts, stopped flag and outcome. Emit failed cycles as failures even when a later cycle recovers. Do not call a live process healthy merely because it exists; no custom healthcheck/automatic alert or restart policy is claimed.
- Measure backlog separately after a successful batch return: pending orders with nonnull deadline at/before a freshly captured PostgreSQL wall clock; publish count, observation time, oldest deadline and overdue seconds. This is an MVCC observation that can include locked rows and change immediately; it is not derived from SKIP LOCKED output or a distributed snapshot. Missing observation after database failure is NULL, never zero. No queue index/performance gain is claimed without a separate measured workload.
- Add `compose.worker.yaml` with an explicit `workers` profile, no published ports/mounts, `init: true`, `restart: "no"`, 30-second stop grace and configurable interval/limit. Require separately confirmed expected database and administrator; safe env examples use placeholders. Build/migrate/grant/provision the actor before starting it. Enabling/stopping this service uses explicit overlay/project/env arguments and does not operate Codex reminders or host cron.
- Current application image/API label becomes 1.3.0; HTTP paths/stock/lifecycle/deadline rules and schema remain unchanged. Existing running environments are not upgraded or scheduled automatically. Historical data, prices, payments, source license and source query evidence remain untouched.

## Required evidence

Use meaningful tests for bounds, finite cycles/fixed delay, signal handlers/interruptible wait/restoration, database failure recovery/reconnection, revoked authority/target refusal, partial failures and unavailable metrics. Use real PostgreSQL for exact backlog/NULL/terminal rules, locked-row observation and stopping during a controlled release without a second transaction. Verify worker/default Compose isolation and the existing five-service CI guard.

Run complete PostgreSQL checks, role probe, strict OpenAPI and unchanged-schema restore. Demonstrate actual worker container cycles, release/restart behavior and SIGTERM from observed JSON events rather than guessed delays, in a new isolated fictional database. Retain actual commands/logs/artifacts with bounded secret inspection, independent review and exact-revision hosted CI; stop for technical review afterward.

Persistent oldest inconsistent orders can consume each cycle's attempt limit and starve later records until administrator intervention. Failed cycles/backlog remain observable; this bounded delivery does not add quarantine or promise queue fairness. Programming errors are classified as `unexpected_error` and fail fast without exception details, instead of being mislabeled as database errors.
